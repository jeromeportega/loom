# Epic 5 Review: Skill System

Reviewing `SkillStore`, `SkillSelector`, `SkillGenerator`, and their wiring into the
Supervisor and the MCP/CLI surfaces, with an eye on downstream impact on Epic 6.

## Findings

### Medium — documented, accepted for MVP

**1. `SkillGenerator` works from the worker's log tail, not the full tool-call trace.**
- The epic envisioned extracting skills from "the tool call sequence." But the worker's
  individual bash commands are audited into the *worktree's* `.loom/loom.db` (the
  Epic 3 audit-fragmentation issue), not the main DB. So `SkillGenerator` works from
  what the main DB *does* have: the story spec, the worker's `summary`, and `log_tail`.
- That is a thinner signal than a full trace, but adequate for "was there a novel
  pattern" — and honest about what is available.
- **Revisit when**: the audit-fragmentation issue is fixed (worker hook points at the
  main DB); then `SkillGenerator` can use the real command trace.

**2. Skill generation cost scales linearly with story count.**
- One Haiku call per successful story. Haiku is cheap and the prompt is small, but on a
  large epic this is real spend. There is no opt-out flag yet beyond not supplying an
  API key.
- **Revisit when**: add `policy.agents.skill_generation: on|off|sampled` so teams can
  disable it or sample (e.g. every Nth story).

**3. No evaluation of generated-skill quality.**
- loom writes generated skills and immediately makes them injectable, with no quality
  gate beyond frontmatter/name validation. A low-value or subtly-wrong skill silently
  enters the loop and influences future workers.
- For MVP this is acceptable — `SkillGenerator` is prompted to be strict and most
  stories yield `NONE`; a human can prune `~/.loom/skills/generated/`.
- **This is the strongest argument for the eval-runner discussion** (see the response
  accompanying this review). A future epic should add: a skill-quality rubric, an
  eval harness, and a feedback signal (did injecting skill X improve worker outcomes?).

### Low — minor, deferred

**4. `SkillSelector` keyword matching is shallow.**
- Pure token-overlap with a stopword list — no stemming, no embeddings. "authenticate"
  and "authentication" do not match. The interface is deliberately swappable for an
  embedding-based selector later.

**5. `SkillStore.load()` re-runs `discover()` on every call.**
- `discover()` does a fast-glob + parse of every skill. The Supervisor calls
  `selectSkills()` (which discovers) once per dispatch. With dozens of skills this is
  still sub-millisecond; with thousands it would warrant a cache. Fine for MVP.

**6. Generated-skill naming collisions overwrite silently.**
- Two stories that yield a skill named `loom-testing-async-retry` — the second write
  overwrites the first. Usually fine (the newer one supersedes), but a genuinely
  different skill that happens to collide is lost. Low likelihood; documented.

## What's solid

- **agentskills.io compliance**: skills are standard `SKILL.md` directories — readable
  by hermes-agent and other agentskills.io tools, exactly as the architecture intended.
- **Progressive disclosure**: `discover()` reads only frontmatter; `load()` fetches the
  body on demand — the startup token cost stays low even with many skills.
- **Self-learning compounds within a run**: the Supervisor re-discovers skills on every
  dispatch, so a skill generated by story 1 is available to story 5.
- **Best-effort generation**: `SkillGenerator.afterStory()` cannot throw — a malformed
  LLM response, a bad skill name, or a missing audit entry all yield `null`. Skill
  generation can never break a run.
- **Strict write gate**: generated skill names are validated against the agentskills.io
  naming rules before anything touches disk — no malformed skills enter the store.
- **Fully testable**: every component is unit-tested with temp directories and
  `MockLLMClient` — no API key, no network.
